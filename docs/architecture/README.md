## Main flow: requesting and attending a visit

```mermaid
sequenceDiagram
  actor V as Visitor
  participant C as client
  participant S as server
  participant VY as Vonage Verify
  participant VV as Vonage Video
  participant VM as Vonage Messages
  C->>S: Requests available slots for the property
  S-->>C: Available slots in the next 14 days
  V->>C: Chooses a date and time and enters her name
  V->>C: Enters her phone number
  C->>S: Starts the phone verification
  S->>VY: Starts verification
  alt From a phone, when the operator supports the silent check (server side in progress)
    S-->>C: Check URL
    C->>VY: Opens the check URL in the same tab, over mobile data
    VY-->>C: Back to /verification/return with a code
    C->>S: Sends the silent code
    S->>VY: Checks the code
    VY-->>S: Phone verified
  else Otherwise, or when the silent check fails
    VY-->>V: OTP code by SMS
    V->>C: Enters the code
    C->>S: Sends the code
    S->>VY: Checks the code
    VY-->>S: Phone verified
  end
  C->>S: Books the visit with the verified phone
  alt Slot is still available
    S-->>C: Visit confirmed with property details
  else Slot was taken or is no longer bookable
    S-->>C: 409 SLOT_UNAVAILABLE
    V->>C: Chooses another available time
    C->>S: Retries booking with the same verification
  else Phone verification is invalid
    S-->>C: 422 PHONE_VERIFICATION_INVALID
    V->>C: Verifies her phone again
  end
  Note over S,VM: The confirmation SMS is sent once the Messages feature (#87) is built
  C->>S: Asks for the visitor's room link
  S-->>C: Room link, shown once on the confirmation screen
  C->>S: Asks for a link to share, when the visitor presses the button
  S-->>C: Guest link, which she shares with everyone she invites
  Note over V,VV: On the day of the visit
  C->>S: Enters the room with the room link
  S->>VV: Creates the visit session, the first time someone enters
  S-->>C: Session token
  C->>VV: Joins the visit
```

## Design principles

- **Vonage credentials live only in `server/`.** The client never receives the API secret or the private key; for video it only receives the session token generated by the server
- **All communication with users goes through the server**, so every verification, message and visit is recorded and traceable
- **Vonage webhooks** notify the server of the post-visit call's result, and will notify it of message status once the messages feature is built, so the agency dashboard reflects what actually happened

## Deployment

The client, the server and the database run on Railway as three separate services. The browser only talks to the client's domain: the `client` service proxies `/api` to the server over Railway's private network, as decided in [ADR 0004](../adr/0004-agency-sign-in.md). The server is the only one with Vonage credentials, and its public URL is where Vonage sends the webhooks. The details are in [ADR 0002](../adr/0002-deployment-railway.md).
